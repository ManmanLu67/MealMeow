# Architecture

产品规则的正文。`D:\Project\任务规划\吃饭喵` 与本文件冲突时，以本文件为准。

## 分层

目标是以后能做手机 App，所以规则和命令不绑定任何平台，平台只出现在最外层。

```
miniprogram/        平台壳（微信小程序）。只负责渲染、取设备时区、调用入口
cloudfunctions/     平台入口（微信云函数）。认出登录用户，把请求交给 app/handle.ts
adapters/           存储和外部服务的具体实现。内存、云数据库、手机本地库都放这里
app/                命令层。只认 app/ports.ts 里的接口，不知道数据存在哪
domain/             纯规则。只依赖自己
```

依赖方向只能向下。`test/architecture.test.ts` 检查这些规则，违反会让 `npm test` 失败：

- `domain/` 只能 import `domain/` 自己，不出现 `wx`、`window`、`localStorage`、`process`、`require` 等平台 API。
- `app/` 只能 import `./` 和 `../domain/`。不 import `adapters/`，不出现平台 API。
- `adapters/` 只能 import `app/ports.ts` 和 `app/types.ts`，不能调用命令。
- `domain/` 和 `app/` 不读时钟，也不用随机数。时间只能从调用者传进来的 `now`，所以手机端和云端各自提供时钟，测试也能固定它。

换平台时要写的只有三样：一个新的 `Store` 实现，一个把平台请求变成 `app/handle.ts` 的 `Request` 的入口，一个新的界面。规则、命令和测试不动。`app/handle.ts` 是与平台无关的入口，调用者 ID 只来自平台的登录态，请求体里的 `userId` 一律忽略，审核结果没有对应的页面动作。

手机端会遇到的差别，现在先写下来，不在这一版实现：

- 手机本地库没有云端定时器。结算要在 App 启动、回到前台和后台任务里调用 `runDueJobs`，用同一个函数。
- 内容安全在手机上要调后端接口，回调改成轮询或推送，最终都落到 `applyReview`。
- 时区取设备时区，和现在一致。
- 要换到多设备同步时，需要后端存储和账号，`Store` 的云实现可以直接复用。

## Components

- `domain/` 纯规则。不依赖微信、云开发、数据库。
- `miniprogram/` 三个 Tab：首页、图鉴、我的。全屏页：打卡、领养、纪念册、饭点、提醒、声音与震动（`pages/settings/sound`）、关于。没有 `/pet`。页面外观已锁定，以这些页面为准；`DESIGN.md` 开头的锁定说明优先于后面的旧稿。页面只渲染读模型，不重算规则。数据经 `miniprogram/utils/api.js` 这一个入口调用云函数。`config.usePreviewData` 为 true 时页面读 `preview.js`。
- `cloudfunctions/api` 用登录 openId 调 `handle`。有库时认识全部页面动作，包括 `me` 和 `memorial`。没有库时只替换 `home` / `sync`，其余返回 `unknown_action`。内容安全回调先验签名，再按追踪号写回。`cloudfunctions/settle` 每分钟调 `runDueJobs`。页面动作不拆成多个云函数。
- `app/` 是对 `Store` 的命令：`handle.ts` 与平台无关的入口，写命令是用户同步、打卡、口粮、零食、删除、领养，读命令是 `home`、`gallery`、`adoptView`、`me`、`memorial`。`views.ts` 只读。`user.ts` 同步用户和时区，`checkin.ts` 饭点、打卡、口粮、删除，`snack.ts` 零食，`settle.ts` 结算、审核回调、领养，`schedule.ts` 补结算任务，`media-check.ts` 提交照片并接收回调，`ports.ts` 存储接口。同一用户的写命令走 `Store.runExclusive` 串行。
- `adapters/memory/` 内存存储，测试用。`adapters/cloud/` 是同一套 `Store` 的云数据库实现，另有微信内容安全的提交和签名校验。
- 当前主体是个人。`subjectId` 只能等于本人 `userId`。

## Data flow

打卡是事实，结算是任务。事实在窗口内可增删改。任务只在窗口结束后、审核有终态时读一次。

1. 选图只进入预览。点「完成打卡」才写 `meal_records` 和审计事件。不改饥饿值，不驱动结算。预览关掉之后，这一步先把手机临时路径传到云存储，记录里只存 `cloud://` 文件号；上传失败不打卡。已经是 `cloud://` 的路径不再传一次。
2. `MealCompleted` 只作审计，不喂宠物。
3. `meal_records.status` 只有 `checked_in` 和 `exempt`。没有 `open`。漏餐不写记录。照片是数组，首张是主图。
4. 每个该结算的餐次都有 `settlement_jobs`。保存饭点、用户每次进入、定时器每分钟扫描前，都会补当天和次日的任务，只补缺，不改已有任务的状态。定时器只扫 `windowEndAt` 已过且 `status = 'pending'` 的任务。
5. `FeedingStrategy.evaluate(subjectType, date, meal, participants)` 只返回 `{ outcome: 'fed' | 'starved' }`。参与者由任务层组装。`'group'` 直接拒绝。
6. 宠物域再改饥饿值。没有存活宠物则不改。`settlements` 写入后不再改。

## 饥饿

只在宠物域。漏餐 +1。吃到按档恢复：6–8 到 5，3–5 到 2，1–2 到 0，已经是 0 不变。9 死亡后不变。页面只显示吃饱、有点饿、很饿、濒危、死亡。

死亡由结算写入：`alive = false`、`endedOn`、陪伴天数（领养日到死亡日，含）、用户的 `diedOn` 和冷却截止。死亡时刻取该餐的窗口结束。窗口在领养时刻之前结束的餐次，不计入新宠物。

## 连续天数

一天三餐都是打卡或口粮，这一天才算完成。图鉴可以显示这个数字。它不是饥饿值。

- 从哪天往回数：今天三餐都完成，从今天数。今天还有餐次没到或在窗口内，从昨天数，不算断。今天已经漏了一餐，为 0。
- 先领养：没有早于领养日的完成日。活着只算领养日及之后的连续完成日。死亡后这些天不再计入。个人时间从死亡日的下一天重计。
- 先打卡：活着按完成日计，不减。死亡后，从当前这段连续天数里减去领养日到死亡日（含）重合的那些天。
- 同一天既领养又第一次打卡，算先领养。
- 领养过不止一只时，用户保留每只已死亡宠物的在世区间，这些天不会因为领养了新宠物而被算回来。
- 死亡清空的是这只宠物和它的饥饿。不清空图鉴，也不把个人连续天数整体归零。

## 审核

不判断照片是不是一顿饭。上传的图仍走微信内容安全。预览关掉之后，页面先把照片传到云存储，内容安全拿到的是云文件号，不是手机临时路径。打卡写好之后按张提交，追踪号记在记录和 `traces` 里。某一张提交失败不撤掉打卡，那张保持 `pending`。回调先验签名，再用追踪号找到用户、日期和照片，不采用事件体里的用户。一餐多张时每张单独审核，**一张通过整餐就通过**，全部驳回才驳回，还有照片没回就继续等。替换过的照片的迟到回调被拒绝。零食同样提交，结果只决定图鉴里这张图能不能留。

- 通过：按吃到结算，只一次。
- 驳回：这餐作废，按漏餐结算，只一次。
- 未回：任务 `waiting_review`，宠物冻结。结果可以在窗口结束前到达，到达后只写记录，窗口结束时直接按终态结算。
- 窗口结束后 2 小时仍无结果：`manual_review`。不自动通过，不自动驳回。宠物继续冻结。复核出结论后再结算一次。
- **冻结是整体的。** 同一用户有任务在 `waiting_review` 或 `manual_review` 时，其余已到期的任务也不结算，等冻结解除后按窗口结束时间、早中晚的顺序结算。
- 应急口粮没有图片审核，窗口结束后按吃到结算。口粮和打卡互斥：一餐已有口粮时不能「完成打卡」，先删除口粮。结算前删除口粮退回当月额度。
- 没有记录的任务，窗口结束后按漏餐结算。
- 未结算前删除会撤掉记录。没有新的打卡或口粮时，结算按漏餐。若任务正挂在冻结状态，删除后任务放回 `pending` 并立即结算。已结算后删除只隐藏照片。

红点只表示窗口内还没打卡。打卡完成或窗口结束，红点消失。审核未完成不留红点，也不因此改宠物。

## 零食

窗口外的打卡算零食。它是一份照片记录，不属于任何一餐，不进结算，也不影响宠物。

- 一小时内的打卡合并成同一份，以这一份的第一次打卡为锚（不是滑动窗口，连续吃也会在一小时后另开一份）。
- 按逻辑日归档，每日 04:00 换日。04:00 前的零食属于前一个逻辑日，合并只看当天已有的零食。
- 要照片、要审核，回调按零食的照片 ID 对应，一张通过即可（和三餐同一套 `aggregateReview` 规则，但零食的审核结果只决定这张图能不能留在图鉴里）。
- 不改饥饿值、不进结算、不占口粮额度、不算「一天三餐都完成」，也不计连续天数。不设每日上限。
- 饭点里可以另记一份零食，不代替这一餐，也不绕开「一餐一条记录」。窗口外的打卡仍然直接记零食。
- 图鉴里零食单独显示一行。删除零食随时可以，不需要先看有没有结算。

## 页面和范围

- 没有独立宠物页。没宠物时首页是抽象人和「领养」，相机只是圆框和相机符号，位置和大小与有宠物时相同。只有当前宠物已死、冷却还没结束时，首页才出现纪念册入口。没有死亡记录时入口不出现。纪念册列表为空只显示空列表，不改首页。冷却结束后回到没有宠物的首页，入口也收起。活着时首页不贴情绪词。左上角是饥饿、健康、等级。陪伴天数在半屏。当天打卡留下的照片停在首页，从左到右是早餐、午餐、晚餐，不按打卡后的分钟数消失。打卡往食盘里加一盘丸子，越靠近下一顿饭点丸子越少，到饭点清空。口粮和零食不加丸子。
- 打卡页：拍照、相册、主按钮「完成打卡」、次级应急口粮。已打卡态只有替换照片和删除打卡。一餐可多张，首屏一张主图。`checkin` 和 `exempt` 请求不带日期，日期由服务端按用户时区算，客户端传来的日期被丢弃；`deleteCheckin` 带日期，因为以后图鉴里能删以前的记录。有待打的餐时，点相机先选这一餐或零食；没有待打的餐时直接进零食记录页。`snack` 请求只带照片、不带日期和餐次；`deleteSnack` 带日期和这份零食的起点时刻。
- 声音与震动在「我的」里是独立一页。音效默认关，震动默认开，偏好存本机，不上云。
- 饭点修改次日 04:00 生效，本轮不限次数。三餐的打卡时间不能重合。窗口是饭点前后 1 小时，左闭右开，所以相邻饭点至少隔 2 小时；恰好 2 小时只是端点相接，不算重合。饭点不能落在 03:01 到 04:59，否则窗口会跨过逻辑日界线。连续两天改饭点，前一次的改动先并入生效饭点，再放新的待生效饭点。逻辑日从该时区 04:00 开始。时区由客户端按设备当前时区传入，服务端不用服务器时区。
- 应急口粮每月 2 个，逻辑月 1 日 04:00 重置。只在有存活宠物、窗口内、未结算、还有额度时可用。
- 领养要求没有存活宠物且冷却已过。领养时取名，最多 6 个字（按 Unicode 字符计），可不填（默认「小饭」），取了不能改，死亡后仍留在纪念页。挑选时页面写「请选择」，四个选项显示为猫、狗、鸟、鱼，不选就是黑猫。领养时刻写入宠物，窗口在此之前结束的餐次不计入这只宠物。没有宠物时首页是抽象人，相机只是圆框和相机符号；领养之后首页换成对应的动物，相机用该物种的。
- 冷却从死亡所在逻辑日起 7 个逻辑日，截止日 04:00 可再领养。
- 抠图、涂抹、餐盘拼图不在本轮。抠图上线后，原图保留到「该餐窗口结束」和「该逻辑日次日 04:00」二者中较晚的时刻，之后只留贴纸。本轮图鉴保存打卡照片，不按日界线删除。
- 小组不启用。策略只回答算不算吃到。参与者怎么来、`windowEndAt` 怎么算、冷却给谁，都在策略外面。主体不变，这三件不能做。

## Boundaries and constraints

- 领域层不调用 `wx` 或云数据库。
- 不要新增 `groups`、`group_members`，不要实现 `GroupFeedingStrategy`。
- `subjectType` 留在任务、结算结果和策略参数上，是为了以后换主体。现在没有按他人 ID 读写的路径。
