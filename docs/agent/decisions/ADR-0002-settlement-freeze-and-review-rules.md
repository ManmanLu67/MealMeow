# ADR-0002: 结算任务、冻结和审核的补充规则

- Status: accepted（第 3 条由用户改为「一张通过即可」；第 1、2、4 条用户同意默认）
- Date: 2026-11-13

## Context

`feat/store` 上的存储、打卡、结算命令单独测试都通过，但串起来有缺口：宠物不会死，正常打卡喂不到宠物，大部分餐次没有结算任务，连续改饭点会丢掉前一次。修这些缺口时，有几条规则 `ARCHITECTURE.md` 没写明，需要先定下来。

## Decision

规格已经写明的部分按规格改。下面四条是规格没写，这里取的默认：**需要用户确认**。

1. **冻结是整体的。** 同一用户只要有任务在 `waiting_review` 或 `manual_review`，该用户其余已到期的任务也不结算，排队等冻结解除，再按窗口结束时间、早中晚的顺序结算。理由：饥饿值的档位恢复和 +1 不可交换，按餐次冻结会让结果取决于审核回调到达的先后。
2. **口粮和打卡互斥。** 一餐已有口粮记录时，「完成打卡」被拒绝，先删除口粮再打。结算前删除口粮会退回当月额度。结算后删除口粮不退额度。理由：口粮没有图片审核，被打卡覆盖会吞掉额度又改变审核路径。
3. **多张照片逐张审核，一张通过即可。** 每张照片有自己的审核结果。只要有一张通过，整餐就通过，不必等其余照片。全部驳回才算驳回，还有照片没回就继续等。回调按照片 ID 对应，替换照片后旧照片的迟到回调被拒绝。理由：规格写「一餐可多张」，没写聚合方式；用户选择一张通过即可。
4. **饭点不能让窗口跨过凌晨 4 点。** 03:01 到 04:59 的饭点被拒绝。理由：窗口是饭点前后 1 小时，跨过逻辑日界线时同一个窗口分属两个逻辑日，`日期不符` 和 `不在打卡窗口` 会同时拒绝一次合法打卡。

下面几条是实现层面的决定，规格没有冲突：

- **结算任务由三个入口补齐：** 保存饭点、用户每次进入时同步时区、定时器每分钟扫描前。每次补当天和次日，只补缺，不改已有任务的状态。改饭点和换时区时刷新仍是 `pending` 的任务窗口。
- **审核结果可在窗口结束前到达。** 只改记录，不动任务。窗口结束后任务在冻结状态时，终态把它放回 `pending` 并结算。
- **死亡由结算写入。** 饥饿到 9 时写 `alive = false`、`endedOn`、陪伴天数、用户的 `diedOn` 和冷却截止，死亡时刻取该餐的窗口结束，补跑也落在正确的逻辑日。
- **领养时刻之前结束的窗口不计入新宠物。** 用 `adoptedAt` 判断。
- **连续天数的锚点。** 今天三餐未全完成且没有漏餐时，从昨天往回数。今天已经漏了一餐则为 0。
- **多只宠物的连续天数。** 用户保留 `pastPets`，每只死亡宠物的在世区间都从个人连续天数里扣掉，不会因为领养了新宠物而被算回来。
- **同一用户的写命令串行。** `Store.runExclusive(subjectId, fn)`。内存实现用 Promise 链，云数据库适配器用事务或锁文档。
- **口粮额度退回以口粮记录的逻辑月为准。** 跨月的口粮删除不退到新的月份。

## Consequences

- `Store` 接口增加 `runExclusive`、`listUserIds`、`listFrozenJobs`。云数据库适配器必须实现它们。
- `MealRecordDoc` 增加 `photoReviews`，`PetDoc` 增加 `adoptedAt`，`UserDoc` 增加 `pastPets`。
- 规则 1 到 4 如果用户不同意，需要改回，影响 `app/settle.ts`、`app/checkin.ts`、`domain/meal.ts`、`domain/settlement.ts` 和对应测试。
- 整体冻结意味着一次长时间的人工复核会让这位用户的宠物整体停住，直到复核有结论。这是 ARCHITECTURE 本来要的「宠物继续冻结」的直接结果。

## Rejected alternatives

- **按餐次冻结。** 结果取决于顺序，且已复现。
- **口粮覆盖打卡。** 额度被吞，也没有地方记。
- **照片只审第一张。** 后几张可以绕过内容安全。
- **任何一张驳回则整餐作废，全部通过才算通过。** 最初的默认。用户改为一张通过即可，原因是一餐里有一张合格的照片就说明吃了这一顿，不应该因为另一张无关的照片被误伤。代价是内容安全驳回的照片仍会留在记录里，只要另一张通过就不影响结算，页面展示时要按 `photoReviews` 过滤掉被驳回的照片。
- **跨日界线的窗口拆成两段。** 窗口语义变复杂，页面胶囊也要双向处理。限制饭点范围更简单，代价是 03:01 到 04:59 不能设为饭点。
- **只在保存饭点时建任务。** 没改过饭点的用户没有任务，漏餐不扣饥饿，已复现。
