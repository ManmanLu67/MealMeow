# 结算 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 窗口结束后，按餐次记录的最终状态和审核终态结算一次。没有终态时宠物冻结。饥饿到 9 时宠物死亡并进入冷却。

**Architecture:** `app/settle.ts` 的 `runDueJobs` 先 `topUpAllJobs`，再对每个用户在 `store.runExclusive` 里调用 `runDueJobsFor`。它读 `listPendingJobs`，对每条任务调用已有的 `settleStep` 和 `evaluateFeeding`，饥饿变化只调用 `nextHunger`。审核回调 `applyReview` 只写记录里的照片结果，再走同一条结算函数。死亡和领养也在这个文件。

**Tech Stack:** TypeScript，`node --test`。不调用微信内容安全接口；测试直接调用 `applyReview`。

**Spec:** `docs/agent/ARCHITECTURE.md` 的审核、饥饿、连续天数。规则补充见 `docs/agent/decisions/ADR-0002-settlement-freeze-and-review-rules.md`。

## Global Constraints

- 扫描条件是 `windowEndAt` 已到且 `status === 'pending'`。
- 审核通过：`fed`，按档恢复。驳回或没有记录：`starved`，饥饿 +1。
- 审核结果按照片记。一张通过整餐就通过，全部驳回才驳回，还有照片没回就继续等。
- `review === 'pending'` 且未到截止时间：任务改为 `waiting_review`，饥饿不变。
- 到达 `reviewDeadline` 仍无结果：任务改为 `manual_review`，饥饿不变。不自动通过，不自动驳回。
- 截止时间是窗口结束后 2 小时，用 `REVIEW_WAIT_MS`。
- **冻结是整体的。** 同一用户只要有 `waiting_review` 或 `manual_review` 的任务，其余到期任务不结算，等冻结解除后按窗口结束时间、早中晚排序结算。
- 已有 `settlements` 行的餐次不再写第二次，饥饿不再变。
- 窗口在 `pet.adoptedAt` 之前结束的餐次，不改新宠物的饥饿值。
- `pets.alive === false` 或没有宠物时，可以写结算结果，但不改饥饿值。
- 饥饿到 9：写 `alive = false`、`endedOn`、陪伴天数、用户的 `diedOn` 和 `cooldownUntil`。死亡时刻取该餐窗口结束。
- 领养要求没有存活宠物且冷却已过。领养写 `adoptedOn`、`adoptedAt`，并把上一只的在世区间记进 `pastPets`。
- 所有写命令走 `store.runExclusive(userId, ...)`。命令内部不嵌套调用同一用户的 `runExclusive`。
- `subjectType: 'group'` 不在这里实现。`evaluateFeeding('group', ...)` 保持抛错。

## Review Focus

- 没有餐次记录的待执行任务仍然挨饿。测试放在任务 1。
- 审核挂起超过 2 小时后宠物饥饿值与结算前相同。测试放在任务 1。
- 一餐在等审核时，其他餐次不会先结算。结果与审核到达的先后无关。测试放在任务 1。
- 同一次通过结算跑两遍，饥饿值只变一次。测试放在任务 2。
- 审核结果在窗口结束之前到达，也不会被丢掉。测试放在任务 2。
- 照片被替换后，旧照片的迟到回调不会落到新照片上。测试放在任务 2。
- 两个扫描同时跑，每餐只结算一次。测试放在任务 3。
- 饥饿到 9 时宠物死亡，冷却期内不能领养，冷却结束可以。测试放在任务 3。

### Task 1: 跑到期任务

**Files:**
- Create: `app/settle.ts`
- Test: `test/settle-run.test.ts`

**Interfaces:**
- Consumes: `settleStep`、`evaluateFeeding`、`nextHunger`、`aggregateReview`、`reviewDeadline`、`Store`
- Produces:
  - `runDueJobs(store: Store, now: Date): Promise<{ settled: number, frozen: number }>`
  - `runDueJobsFor(store: Store, userId: string, now: Date): Promise<{ settled: number, frozen: number }>`。调用方必须已经持有该用户的 `runExclusive`。

- [ ] **Step 1: Write the failing test**

```js
test('a missing record starves and a pending review freezes the whole pet', async () => {
  const end = new Date('2026-11-13T04:00:00.000Z')
  const store = await seededStore({}, { hunger: 4 })
  await job(store, 'breakfast', end)
  await job(store, 'lunch', end)
  await store.saveRecord(record({ meal: 'lunch' }))
  const first = await runDueJobs(store, end)
  assert.equal((await mustPet(store)).hunger, 5)
  assert.equal((await store.getJob('u', '2026-11-13', 'lunch')).status, 'waiting_review')
  await runDueJobs(store, new Date(end.getTime() + 2 * 60 * 60 * 1000))
  assert.equal((await mustPet(store)).hunger, 5)
  assert.equal((await store.getJob('u', '2026-11-13', 'lunch')).status, 'manual_review')
  assert.equal(first.settled, 1)
  assert.equal(first.frozen, 1)
})
```

另加：早餐在等审核时，同一天的午餐漏餐不结算，任务仍是 `pending`；审核先到或扫描先到，最终饥饿相同。

Run: `node --test test/settle-run.test.ts`
Expected: FAIL，`runDueJobs` 不存在。

- [ ] **Step 3: Implement `runDueJobs` and `runDueJobsFor`**

`runDueJobs` 先 `topUpAllJobs(store, now)`。对每个用户在 `runExclusive` 里调用 `runDueJobsFor`。`runDueJobsFor` 先把等审核已过截止的任务改成 `manual_review`，再按窗口结束时间、早中晚排序处理 `pending` 任务：`frozen` 的只改状态；用户名下有冻结任务时，`settle` 的任务跳过，留给下次。结算时调用 `evaluateFeeding('personal', date, meal, [{ status }])`，再用 `nextHunger`，然后写 `settlements`，把任务标成 `settled`。

### Task 2: 审核终态只结算一次

**Files:**
- Modify: `app/settle.ts`
- Test: `test/settle-run.test.ts`

**Interfaces:**
- Consumes: `runDueJobsFor`、`aggregateReview`
- Produces: `applyReview(store, caller: { userId: string }, input: { date: string, meal: MealType, photo: string, review: 'passed' | 'rejected' }, now: Date): Promise<{ ok: true } | { ok: false, error: string }>`。`photo` 是照片 ID，对应 `photos` 里的一项。

- [ ] **Step 1: Write the failing test**

```js
test('takes a result before the window ends, then settles when it ends', async () => {
  const end = new Date('2026-11-13T04:00:00.000Z')
  const store = await seededStore({}, { hunger: 8 })
  await job(store, 'lunch', end)
  await store.saveRecord(record())
  const early = new Date('2026-11-13T03:05:00.000Z')
  await applyReview(store, { userId: 'u' }, { date: '2026-11-13', meal: 'lunch', photo: 'a', review: 'passed' }, early)
  assert.equal((await store.getRecord('u', '2026-11-13', 'lunch')).review, 'passed')
  assert.equal((await store.getJob('u', '2026-11-13', 'lunch')).status, 'pending')
  assert.equal((await mustPet(store)).hunger, 8)
  await runDueJobs(store, end)
  assert.equal((await mustPet(store)).hunger, 5)
})
```

另加：多张照片时一张通过一张未回，任务冻结；另一张驳回后立刻按漏餐结算。照片被替换后，旧照片 ID 的回调返回「照片已替换」，不改新照片。已结算后再收回调返回 `already_settled`，饥饿不再变。

- [ ] **Step 2: Run test to verify it fails**

Run: `node --test test/settle-run.test.ts`
Expected: FAIL，`applyReview` 不存在。

- [ ] **Step 3: Implement `applyReview`**

在 `runExclusive` 里执行。按照片 ID 找到 `photos` 里的位置，写 `photoReviews`，用 `aggregateReview` 更新记录的 `review`。聚合结果仍是 `pending` 时只写记录。有终态且任务在 `waiting_review` 或 `manual_review`，把任务改回 `pending` 后调用 `runDueJobsFor`。任务仍是 `pending`（窗口没结束），不动任务。已是 `settled` 返回 `{ ok: false, error: 'already_settled' }`。

```js
test('hunger 9 kills the pet, records the end day, and starts the cooldown', async () => {
  const end = new Date('2026-11-13T04:00:00.000Z')
  const store = await seededStore({ adoptedOn: '2026-11-01' }, { hunger: 8 })
  await job(store, 'breakfast', end)
  await runDueJobs(store, end)
  const dead = await mustPet(store)
  assert.equal(dead.alive, false)
  assert.equal(dead.endedOn, '2026-11-13')
  assert.equal(dead.companyDays, 13)
  const owner = await store.getUser('u')

  assert.equal(owner.cooldownUntil, '2026-11-19T20:00:00.000Z')
})
```

另加：冷却截止前一分钟领养返回「冷却中」，截止时刻领养成功，新宠物饥饿为 0 且 `user.diedOn` 清空、`pastPets` 记下上一只。领养之前结束的窗口，不改新宠物的饥饿值。两个 `runDueJobs` 同时发起，每餐只结算一次，结果与串行相同。
