# 本机版 MVP

> 2026-11-23。产品规则仍以 `docs/agent/ARCHITECTURE.md` 为准。这一份只写这一版怎么在没有云的情况下跑起来。

## 意图

先在一台手机上能用：吃饭打卡，宠物按现有规则吃到或挨饿。不接云，不上传照片，不走微信内容安全。云函数、云数据库和审核代码留在仓库里，这一版不调用，以后再接。

## 目标

- 第一次打开先设置昵称，然后才能用。
- 打卡、口粮、零食、领养、图鉴、纪念册、饭点都走现有命令。本地打卡马上算吃到。宠物在本机结算。
- 照片在手机上压低画质后存进本地文件，记录里只存路径。
- 本月和上月之外的照片删掉。吃没吃过的记录留下。更早的日子在图鉴里仍有打卡痕迹，只是没有照片。连续天数仍按打卡记录计算。
- 可以把记录导出成 JSON，发到微信聊天；换机后导入这些记录。照片不在文件里，换机后打不开。

## 非目标

- 不部署云函数，不配置 `MEAL_MEDIA_TOKEN`，不调用内容安全。
- 不删除 `cloudfunctions/`、`adapters/cloud/`、`app/media-check.ts`。
- 不改已经锁定的页面外观。新增的只有第一次的昵称页，以及「隐私与关于」里的导出、导入。
- 不做小组、跨用户、独立宠物页、抠图、涂抹、餐盘拼图、订阅消息。
- 不把照片打进导出文件。

## 做了也算失败

- 页面里重写一套饥饿或连续天数。
- 为了本机版改掉云端那套命令的结算含义。
- 把照片放进 `wx.setStorage`。
- 删掉早期打卡记录，导致连续天数从上个月重计。

## 做法

考虑过两条。

1. 把现有的 `domain/` 和 `app/` 编译进小程序，加一个本机版 `Store`。页面改调这个入口。云端代码留着不调用。规则和现有测试是同一套。
2. 在小程序页面里另写一套本地规则，不走 `handle`。文件少，但现有测试盖不住正在跑的逻辑。

选定第 1 条。原因是饥饿、结算、连续天数已经测过，架构本来就把换存储留在 `adapters/`。

## 已经定下的行为

- 主体仍是个人。本机生成一个用户号，存在本地，之后不变。不使用微信登录号。
- 没有昵称时，打开小程序先进入一页，标题是「请设置你的昵称」。去掉首尾空白后不能是空。通过后才进首页。这一版不在「用户」页再做修改昵称。
- 压图只用 `wx.compressImage`，不做马赛克，不用 Canvas。
- 记录进本地缓存。单个 key 最大 1MB，总共 10MB。图片文件进 `FileSystemManager` 的用户目录，上限 200MB。记录的 `photos` 只存本地路径。
- 月份沿用现有逻辑月：该时区每月 1 日 04:00 换月。只保留本月和上月的照片文件。更早的照片删文件，并把记录里的路径清掉。记录的 `status`、`review` 保留，所以图鉴仍显示打卡或口粮，连续天数照旧往回数。零食照片同样处理。
- 打卡写入后马上把每张照片记为通过，不等审核。窗口没结束前不结算；窗口结束后，下次打开小程序时用现有的 `runDueJobs` 结算。没有云端定时器。
- 导出是一份 JSON 文件，用 `wx.shareFileMessage` 发到聊天，必须用户点。内容是本机存储里的用户、宠物、打卡、零食、结算任务和结算结果，不嵌入图片字节。导入用会话里的文件，整份替换本机记录。换机后路径对不上的照片，图鉴和首页按没有照片显示。不因为导入再结算一遍历史餐次。

## 留给实现的

- 本机 `Store` 怎么拆 key，只要满足 1MB 上限，并且测试能用注入的存储跑，不碰真实的 `wx`。
- 压缩质量的具体数字。
- 编译进小程序的输出路径。生成物不入库。
- 昵称页只用现有字色和底色，不改其他页。

## 约束

- `domain/`、`app/` 继续不调用 `wx`，不读时钟。时间由小程序传入。
- 页面不重算规则，只渲染读模型。
- 不改 `project.config.json`、`project.private.config.json`。
